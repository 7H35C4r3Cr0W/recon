Local Recon Workspace · OSCP exam-legal by default · and where it goes next

Nabu turns a scan into a plan — and could turn that plan into an agent team.

A PySide6 desktop app and headless CLI that wraps the standard OSCP-allowed enumeration tools, drives them one decision at a time, surfaces findings in a BloodHound-style graph, links inline to HackTricks and Exploit-DB, and writes Obsidian-ready reports. Recon-first, fully offline, no auto-exploitation and no LLM calls at runtime. This page is the whole story on one screen — the finished tool, and the blueprint for augmenting it with an agent-to-agent system.

01

What Nabu is

🛰️ Recon-first, exam-legal by default

The default mode wraps only OSCP-allowed enumeration — nmap/NSE, feroxbuster/ffuf/gobuster, nikto/whatweb, enum4linux-ng/netexec/smbclient, ldapsearch, snmpwalk, dnsrecon and the rest. A single exec chokepoint (shell.py) enforces an allow-list, so nothing outside recon can run.

Credential spraying and an Exploitation tab exist but are separate, opt-in, and human-driven — never part of the default posture.

🧭 One decision at a time

Unlike run-everything scanners, Nabu shows you the exact command, why it runs, and the expected runtime, then waits. You click Run. Findings feed a pattern engine that proposes sensible next steps — text only, never auto-executed.

  • Tier 1 — anonymous/null checks run on one click
  • Tier 2 — single default-cred attempts are shown, you run them
  • Tier 3 — list-driven spraying is gated behind opt-in Spray mode

🕸️ Findings become a picture

Every parsed fact lands in a per-project workspace and a BloodHound-style graph — target → services → findings → artifacts → credentials — that you annotate, re-layout, and export to PNG/SVG.

The reference pane renders the mapped HackTricks page (vendored offline, with an owner-approved live fetch/cache) and a version-aware Exploit-DB lookup, alongside the service you selected.

📄 Reports that drop into Obsidian

Each scan rewrites an Obsidian-compatible report.md — frontmatter, per-service findings, suggested next steps with provenance, and a full command log with timing and exit codes. Nothing about what ran is ever hidden.

A per-project audit trail records every GUI action; an on-demand vault export writes a linked note tree.

02

How the recon actually works

A scan is a staged pipeline, not a single button. Each stage narrows the next.

① Scan → discover

Staged nmap — TCP top-1000 for speed, then -p- for completeness, then -sCV on found ports, plus UDP top-100. The parser fills discovered_services, which forks every downstream branch. 83 nmap presets plus an NSE picker cover the common script batteries.

② Fan out per service

26 read-only service modules key off the open ports — http/vhost, smb (tiered null→guest→shares→RID), ftp, ssh, ldap, smtp, nfs, snmp, and the UDP long tail. Each module has the same contract: triggers → commands → parse → suggest. Anonymous wins auto-write a credential entry the other modules reuse.

③ Parse into findings

Parsers turn raw tool output into structured findings — a leaked source file, SMB signing disabled, a readable share, a version banner. The Discovered-URLs table gives web content discovery a sortable, exportable site map with source/backup-disclosure flags.

④ Suggest the next step

A 52-file pattern library matches findings and emits cited recon next-steps (every entry carries a # source: from a real box). They pre-fill the command builder on click — you always pull the trigger.

03

How the attack modules work

A separate, owner-authorized Exploitation tab extends the same "you select it, you run it" model to attack tools. It is a decision-aid, not an autopwn chain.

🎯 Build → confirm → run → parse

Per discovered service, the catalog pre-fills the exact command from the profile plus a chosen vault credential. Nothing runs until you press Run and confirm a dialog that names the target. One command per Run — no chaining, no scan-to-exploit pipeline. Output streams back and auto-parses into loot.

The guardrail is the human, not a block-list. Recon mode stays allow-listed; only a confirmed Run from this tab reaches exploit mode.

⚿ Attacker vs victim, tied to the scan

runs_on=attacker actions are single Popen-safe commands you Run from Kali; victim actions (SUID checks, GTFOBins, reverse shells) are copy-only, never executed here. The picker surfaces the surfaces open on this box first and warns when you act on a service the scan never saw.

🗂️ A decision-aid, not a CVE hoard

183 services / ~3,187 actions cover fingerprinting, enumeration, default/weak-cred checks, config/loot reads, and generic offensive technique classes — the full AD attack catalog, web SQLi/SSRF/LFI/SSTI/upload/deserialization primitives, the potato family, GTFOBins, file transfers, privesc enumeration. Box-specific weaponized CVE PoCs are deliberately excluded — crafting the per-box exploit is the pentester's job.

🧰 Standalone helpers

A copy-only msfvenom payload builder (exam-safe reverse shells + matching listener), a GTFOBins lookup, a hashcat/john cracking helper, a credential vault with reuse propagation, and a multi-network Ligolo pivot map. All copy-first; loot is shown in full, never redacted.

04

The safety model

Exam-legal

Default recon mode is strictly allow-listed at the single exec chokepoint. No Metasploit exploitation modules, no SQLMap, no commercial scanners, no LLM calls at runtime, no automated exploit chains, no PoC download/execute. The tool runs offline against your authorized target only. Spraying and exploitation are opt-in and human-confirmed, and never touch anything but the assigned target.

05

Boxes it has completed or been fed — what "tested" means

"Completed" is not "watched a walkthrough." Each box is a live field test: recon and attack driven against the live machine, foothold→root where practical, with the tool's own modules proving they parse and behave — then a real gap it exposed gets fixed, re-tested green, and committed. 50 boxes so far (HTB, Proving Grounds, VulnLab, a Pro Lab).

1

Scan & drive

Run Nabu end-to-end against the live box — recon then attack — as a real operator would.

2

Find the gap

Where a parser misses, a command is wrong, or a generic technique is absent — that is the bug.

3

Fix & re-test

Fix the engine, add a fixture, re-run the four gates (types, tests, lint, format) until green.

4

Commit

Push to GitHub. The same http/ftp/snmp bugs never come back — each box hardens the next.
