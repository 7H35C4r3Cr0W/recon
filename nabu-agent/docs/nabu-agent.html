Internal · Agent-driven recon platform · built on the Nabu engine

A scan becomes an autonomous recon team — with a human at the gate.

Nabu Agent turns the classic Nabu desktop recon tool into an internally-hosted web platform. An operator logs in, creates a scope-limited engagement, and launches an autonomous recon run against an IP or IP/range. A supervisor fans out one agent per port/service plus research and report-writer agents; each does its own work, and the platform streams live progress and hands back a clean report with next steps. Every attack action stays behind an explicit human approval.

01

Brain · Body · Hands

A clean separation of concerns — and of trust. The LLM plans; the platform enforces; the engine executes.

🧠 Brain — you attach it

An internally-hosted, OpenAI-compatible LLM (GPT-5.1 today). Point NABU_LLM_BASE_URL at it and it plans, chooses tools, and writes prose.

It is an untrusted planner: its tool calls are validated and safety-gated before dispatch; its prose is grounded against engine artifacts before an operator sees it. Fully swappable via NABU_LLM_PROVIDER — no vendor lock-in.

🦾 Body — this project

FastAPI edge (REST + live WebSocket), Arq orchestration workers, the engine adapter, Postgres + Redis, and a React/Vite/TS SPA.

It owns state, scope, gates, and audit. Safety is code here, not prompt text.

🛠️ Hands — the Nabu engine

The classic oscprecon recon engine, imported read-only: its 183-service catalog, service parsers, NSE profiles, references, reporter — and its single allow-listed shell.run executor.

Nabu Agent never rebuilds recon knowledge and never modifies src/oscprecon.

01

The five layers

One canonical package (nabu_agent/). The API tier runs no tools; only the worker executes recon, and only through the single chokepoint.

🌐 Web platform nabu_agent/

FastAPI app factory + middleware, pluggable auth (OIDC / local), RBAC, the platform audit log, REST routers, and the WebSocket hub. Reaches the engine only through a read-only facade — the api container drops all Linux caps and runs no tools.

🔀 Orchestration orchestration/

The supervisor + fan-out agent graph on Arq/Redis: a run-state machine, a non-blocking supervisor with a re-trigger-on-last-finisher barrier, run limits (host / concurrency / token caps), admission control (one active run per project), and the human checkpoints.

🔒 Engine adapter engine/

The only importer of oscprecon. Eight typed agent-tools, the read-only gateway, the workspace mapping (one Profile per host), and shell_gateway.py — the single shell.run chokepoint (recon path + the sole human-gated exploit executor).

🧠 Brain seam llm/ + agents/

The LLMProvider contract + OpenAI-compatible adapter (SSE + tool-call reassembly), the tool-calling AgentRunner, role prompts, the SafetyGate, token budgets, and the canonical live-event envelope.

📦 Deploy / ops deploy/

Docker Compose: nginx SPA edge, api, arq worker(s), Postgres, Redis, and a one-shot migrate step. Least-privilege containers (worker drops all caps, re-adds only NET_RAW, seccomp, non-root), internal network, isolated egress, and a policy-invariant CI gate.

🗄️ State

Postgres holds product + orchestration state and read-models; Redis is the queue + live pub/sub + budget ledger; the Profile folder on the workspace volume remains the authoritative recon truth (findings, creds, audit trail, report).

01

The six non-negotiables — enforced in code

Carried over from classic Nabu's exam-legal posture and adapted for an autonomous, networked context. These are structural, not prompt text.

① Read-only engine

src/oscprecon is a non-editable dependency; a CI hygiene job fails any PR that diffs it. A test asserts PySide6 is never imported (headless).

② One shell.run chokepoint

Exactly one module executes tools. An AST test proves no subprocess / shell=True exists elsewhere.

③ Authorized-scope-only

Every target is validated by the engine's own validators and confirmed in the project's scope allowlist before any tool runs — re-checked per host on a range.

④ No blind auto-exploit

Recon is automated; spray/exploit need a per-project toggle plus a human-approved checkpoint. The gate flags live in exactly one executor, unreachable from any agent path.

⑤ Swappable brain

All LLM access goes through one provider seam; endpoint + model come from config. No vendor SDK, no hardcoded endpoint.

⑥ Audit everything

Two trails: the engine's per-project record of what ran, and the platform log of who did what. Every denied authorization is recorded too.

The gate

An agent can propose an attack action (with a rationale and a source), but only a human decision on a server-minted, non-forgeable checkpoint can execute it. The approval — not a tool block-list — is the safety model, exactly as in the classic tool.
